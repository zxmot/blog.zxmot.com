Proposal · v1.0

一个通用对象，
穿越所有接口。

Subject 是一个前后端通用的最小对象约定。 前端对应 TypeScript 的任意对象 const item: object = {}， 后端对应 Go 的 map[string]any。 双方只取自己需要的字段，不需要满屏的结构体与 json:tag。

查看接口 → 前后端示例

01 问题：结构体泛滥与类型僵化

为了在前后端之间传递一个对象，我们写了太多只用于“翻译”的代码。

✗ 传统写法

// 后端：为每个接口定义结构体
type UserReq struct {
    Id   int64  `json:"id"`
    Name string `json:"name"`
    Tags []string `json:"tags"`
    // ... 再加十个字段
}

// 前端：又要维护一份 interface
interface UserReq {
  id: number;
  name: string;
  tags: string[];
}

✓ Subject 约定

// 后端：一个 map 接住所有对象
body := map[string]any{}

name, _ := body["name"].(string)
tags, _ := body["tags"].([]any)

// 前端：任意对象直接发送
const item: object = { ... };
核心洞察： 绝大多数接口传递的对象，本质都是“一袋键值对”。 给它一个统一的形状，比给每个接口单独塑形更经济。

02 Subject 接口

一份 TypeScript 定义，一份 Go 映射。所有字段都是可选的。

TypeScript

interface Subject {
  // 数据库相关
  id?: number;      // 数字 id
  _id?: string;     // 字符串 id
  ztc?: number;     // 创建时间戳（毫秒）

  // 基础属性
  abbr?: string;    // 简写名称
  kind?: string;    // 所属类型
  mark?: string;    // 标记符号
  name?: string;    // 名称
  note?: string;    // 基础备注
  more?: string;    // 更详细的描述
  tags?: string[];  // 多个标签
  value?: number;   // 已废弃，很少使用

  // 树形结构
  subs?: Subject[]; // 包含的子对象数组

  // 扩展属性
  sint?: string;    // 字符串数字，相当于 value
  scss?: string;    // 前端内联样式字符串

  // 业务语义
  link?: string;    // 一个网址链接
}

Go 对应

// Subject 即 map[string]any
var item map[string]any

// 或从 HTTP / DB / 配置文件中读出
body := map[string]any{}
_ = json.Unmarshal(raw, &body)
映射关系： TypeScript 的 object ↔ Go 的 map[string]any ↔ JSON 的 {...}。 三者是同一种东西的三种写法。

03 字段参考

所有字段均为可选。不需要的字段不出现，解析方只取自己关心的。

数据库相关
id number optional
数字形式的记录 id。
_id string optional
字符串形式的 id，常见于 MongoDB 或外部系统。
ztc number optional
数据创建时间戳，单位毫秒。前缀 z 使其在排序时落在最后。
基础属性
abbr string optional
简写名称，用于紧凑展示。
kind string optional
所属类型，用于分类或路由。
mark string optional
任何作用的标记符号，如 "★"、"!"。
name string optional
主要名称，最常用的展示字段。
note string optional
基础备注，一句话说明。
more string optional
更详细的描述，可容纳较长文本。
tags string[] optional
多个标签，用于筛选与检索。
value number deprecated
已废弃，很少使用。新代码请改用 sint。
树形结构
subs Subject[] optional
子对象数组。递归使用同一套约定，天然支持任意深度的树。
扩展属性
sint string optional
字符串形式的数字，作为 value 的替代品。见下方子提案。
scss string optional
前端内联样式字符串，例如 "color:red;font-weight:700"。
业务语义
link string optional
一个网址链接，语义明确，可直接渲染为超链接。
扩展原则： 任何新字段都应保持可选、保持语义单一。 如果某个字段只在极少数场景使用，不要加入核心字段，直接作为普通键值对传递即可。

04 树形结构

subs 让 Subject 天然支持任意深度的树，无需额外定义节点类型。

{ "name": "根节点", "kind": "folder", "subs": [ { "name": "子节点 A", "sint": "1.5" }, { "name": "子节点 B", "subs": [ { "name": "孙节点" } ] } ] }

由于每一层的 subs 元素都是同一个 Subject， 前端和后端的遍历逻辑可以完全递归复用，不需要为每一层定义不同的类型。

05 前后端用法

各取所需，互不打扰。

后端：只取自己需要的字段

// body 来自 HTTP、数据库或配置文件
body := map[string]any{}

// 取字符串字段
name, _ := body["name"].(string)
kind, _ := body["kind"].(string)

// 取数字字段
id, _ := body["id"].(float64)

// 取字符串数字
sint, _ := body["sint"].(string)
vint := utils.ParseStringInteger(sint, 2)

// 取数组
if raw, ok := body["tags"].([]any); ok {
    for _, t := range raw {
        if s, ok := t.(string); ok {
            // 使用 s
        }
    }
}
只取所需： 多余字段自动忽略，缺失字段返回零值。 不需要为每个接口定义结构体，也不需要在解析阶段做类型断言的全覆盖。

前端：任意对象直接发送

// 任意对象即可作为 Subject
const item: object = {
  name: "示例",
  kind: "demo",
  sint: (12.34).toString(),
  tags: ["a", "b"]
};

// 直接作为请求体发送
await fetch("/api/items", {
  method: "POST",
  headers: { "Content-Type": "application/json" },
  body: JSON.stringify(item)
});

无需结构体往返

✗ 结构体往返

JSON → struct → 业务 → struct → JSON
   ↑ 需要 tag   ↑ 需要 tag
   ↑ 类型固定    ↑ 类型固定

✓ Subject 直通

JSON → map → 业务 → map → JSON
   ↑ 零结构体
   ↑ 零 tag

06 子提案：sint

Subject 的一个具体应用，用于承载带小数的数值。

Sub-proposal · sint

用字符串承载数值

sint 是 Subject 中专门用于数值传输的字段。 值恒为字符串形式的十进制数，后端按固定 scale 解析为整数。 它替代了已废弃的 value 字段，彻底规避浮点精度与类型断言问题。

完整规范：参见《sint · 字符串整数传输约定》。

为什么不用 value: number？

方案问题
value: number Go 解析为 float64，业务层无法确定原始整数类型，精度不可控。
value: int64 / int32 前端 JavaScript 所有数字都是 number，无法区分。
value: string 格式不固定，可能是 "12"、"-12.34"、"12%"、"1e3"……无法统一解析。
sint: string 格式明确、解析确定、前后端一致。

前端一行发送

const payload = {
  sint: value.toString()
};
// -12.34 → { "sint": "-12.34" }

后端一行解析

s, _ := body["sint"].(string)
v := utils.ParseStringInteger(s, 2)

if v != 0 {
    // 放心作为业务数据使用
}
注意： ParseStringInteger 对非法输入返回 0。 若接口需要严格校验，请在业务层用正则预校验原始字符串。

07 设计原则

这套提案的取舍，可以归纳为四条。

P1

约定优于结构

用一个通用对象，替代为每个接口单独塑形。类型由字段名约定，而不是由语言类型系统强制。

P2

各取所需

发送方可以附带任意字段，接收方只读取自己关心的。多余字段自动忽略，缺失字段返回零值。

P3

输入宽松，格式明确

接受宽泛的输入，但对关键字段（如 sint）给出严格的格式约定，保证解析确定性。

P4

不绑定语言

提案只描述数据形状与处理逻辑，不依赖 Go、TypeScript 或任何具体框架。任何语言都可以实现。

适用场景

  • 快速迭代的接口，字段频繁增删。
  • 前后端由不同团队维护，同步结构体成本高。
  • 数据来源多样（HTTP、数据库、配置文件），难以统一为固定结构体。
  • 树形、递归、配置类数据，天然适合用通用对象承载。

不适用场景

  • 对强类型、编译期校验有硬性要求的核心业务。
  • 需要 OpenAPI / gRPC 等强 schema 的场景。
  • 字段数量稳定、语义固定的内部接口（结构体反而更清晰）。
