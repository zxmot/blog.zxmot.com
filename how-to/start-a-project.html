01 / MOTIVATION

动机定义 大动机 & 小动机

任何项目启动前，必须同时回答两个问题：它解决的具体场景是什么，以及它是否有机会成为通用方案。 两者缺一不可——只有小动机容易做成一次性脚本，只有大动机容易悬空落不了地。

A大动机 · 可泛化的命题

项目完成后，有机会被抽象为公开的开源提案，适配更多类似场景。

它回答的是：“这件事解决好了，能推广到哪一类问题上？”

大动机决定了项目的抽象层级、接口设计、可扩展性——它不要求一开始就通用，但要求方案不被单一场景绑死。

可开源 可复用 抽象接口 适配多场景

B小动机 · 具体的应用场景

本质就是实际遇到的某个具体问题——一个真实存在的、可被描述的场景。

它回答的是：“谁，在什么情况下，遇到了什么麻烦？”

小动机必须作为案例背景写入项目文档，它是验证大动机是否成立的第一个样本，也是后期演示的天然素材。

真实场景 写入文档 案例背景 首个验证样本
▸
立项检查：如果只能写出小动机而写不出大动机，说明这个项目更适合作为任务直接执行；如果只能写出大动机而找不到具体场景，说明还停留在设想阶段，需要先补一个真实案例再启动。
02 / SOLUTION

方案探索 试探 → 反馈 → 收敛

在确定技术路线之前，需要试探性地尝试不同技术方案，并对每个方案给出大致反馈：预测结果、列出利弊。 这一步不能省——除非项目本身已经非常明确，那就直接塌陷成一个任务。

01

枚举候选方案

针对同一目标，列出至少 2–3 条技术路线。哪怕其中某条明显不靠谱，也先写下来——排除过程本身有价值。

output: 方案清单 + 每条的核心假设
02

试探性验证（Spike）

用最小成本跑通关键路径，获取真实反馈。不做完整实现，只验证“这条路走不走得通”。

output: 可行性结论 + 关键卡点 + 未知风险
03

预测结果与利弊评估

对每个方案给出预判：预期效果、实现成本、维护复杂度、可扩展性、与现有系统的耦合度。

output: 对比矩阵（收益 / 成本 / 风险 / 可逆性）
04

判定：技术路线是否明确？

这是整个流程的关键分叉点。

▸ 明确 → 任务化

技术路线已确定，项目塌陷为可执行的工作任务，直接进入执行方案，无需再探索。

▸ 不明确 → 继续探路

存在多个可行方案或关键未知，需要先做更多验证，再回到决策点。

05

锁定技术路线

确定唯一主线，并记录被放弃的方案及其放弃理由。这份记录是后续复盘与开源提案的重要材料。

output: 技术路线决策记录（ADR）
▸
核心判断：确定好技术方案的项目 = 可执行的工作任务。这个等式把“项目”与“任务”区分开——项目的本质是不确定性，任务的本质是确定性执行。当不确定性被消除，项目就退化为任务，可以直接排期。
03 / EXECUTION

执行方案 压缩环节 · 明细置顶

技术路线确定后，执行方案要求尽可能明细、尽可能压缩。 环节越多，出问题的概率越大——每多一个环节，就多一次交接、多一处理解偏差、多一个失败点。

01

压缩环节

合并可以合并的步骤，消除不必要的中间产物。目标是用最短的链路从输入到达输出。

必须
02

置顶明细

把最关键的步骤、依赖、约束放在方案最前面。执行者第一眼看到的就是最重要的信息。

必须
03

功能概要

每个功能具体干什么、预期效果是什么。不写实现细节，只写行为契约与验收标准。

必须
04

依赖与前置条件

明确执行前必须就绪的资源、环境、权限、数据。前置不清，执行必卡。

必须
05

风险与回退

列出可能导致失败的关键点，以及每个点的回退策略。可逆性是执行方案的安全底线。

必须

功能概要表 / 示例结构

每个功能一行，描述行为与预期效果，作为后续验收的依据。

功能 具体做什么 预期效果
功能 A 描述该功能的核心行为与输入输出 可观察、可验证的结果状态

04 / DEMO

快速演示案例 可选 · 但强烈建议

有的项目需要一个快速的演示案例。它不是最终交付物，而是设计工具——用最小的可运行形态，验证方向、暴露问题、对齐预期。

01验证方向

在投入完整实现之前，先用演示案例确认技术路线在实际运行中的表现是否符合预期。

02暴露问题

很多问题只在真实运行时才浮现。演示案例是成本最低的“踩坑”方式。

03辅助设计

有了可运行的参照，后期的实现过程可以被更好地设计——接口、数据结构、交互流程都会更具体。

▸
可选性说明：演示案例不是每个项目都必需。如果技术路线已经足够明确、实现路径没有未知，可以跳过。但只要存在不确定性，演示案例就是性价比最高的一步。
05 / DELIVERY

交付标准 不止一份测试报告

项目完成后，交付的不止是一个功能测试报告。一个可被他人接手、复用、推广的项目，需要完整的技术文档体系。

📘

操作手册

面向使用者。说明如何安装、配置、运行、排错。目标是让一个没参与项目的人也能独立用起来。

🏗

架构设计

面向维护者。说明系统由哪些部分组成、如何协作、关键取舍是什么、边界在哪里。

📐

技术规格明细

即 Specifications。接口定义、数据结构、参数约束、错误码、性能指标等精确描述。

✅

功能测试报告

面向验收。记录测试范围、用例、结果与已知问题。它是交付的一部分，但不是全部。

▸
交付判断：如果大动机指向开源提案，那么操作手册、架构设计与技术规格明细就是提案的核心材料——它们决定了别人能否理解、复用并推广这个方案。

先问 为什么，再探 能不能，
然后压缩成 怎么做，最后交付 怎么用。
